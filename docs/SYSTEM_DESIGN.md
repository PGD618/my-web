# 系统设计与技术选型（面试用）

> 面试复盘向文档：项目整体介绍 + 功能拆解（不下沉到代码细节）+ 每个技术选型的权衡。
> 与 [my-web-agent/docs/MEMORY_ARCHITECTURE.md](../../my-web-agent/docs/MEMORY_ARCHITECTURE.md)
> 同步更新——那份是开发用的实现细节文档，这份是对外讲述用的决策总结，两者描述的是同一套
> 系统，不应该出现矛盾。

## 一、项目是什么

Zenith Garden：一个基于 Next.js 15 + Obsidian 笔记工作流的个人数字花园网站，核心亮点是
站内常驻 AI 助手「青砚」——基于站主本人的笔记做检索增强问答（RAG），并且能区分"站主本人"
和"访客"两种身份，对访客的问答逐步沉淀成关于站主的结构化长期记忆，使助手"越聊越了解你"。

两个独立仓库，单向依赖：

- **my-web**：Next.js 前端 + 内容引擎（Velite 处理 Obsidian 笔记），负责站点展示和一个
  到 agent 服务的薄代理转发
- **my-web-agent**：独立的 RAG 问答服务（FastAPI + LanceDB），不感知 my-web 的任何实现
  细节，只约定一个通用协议："喂一个 markdown 目录进来，提供问答接口"

## 二、功能点拆解（不涉及代码层面）

1. **内容引擎**：Obsidian 笔记库作为唯一数据源，经切块（按标题边界 + 段落/句子语义边界）
   → embedding → 写入本地向量库
2. **RAG 问答**：用户提问 → 向量检索相关笔记片段 → 拼 prompt → 流式返回答案（SSE）
3. **身份识别**：区分"站主本人"和"匿名访客"，决定接下来的记忆写入权限不同
4. **长期记忆系统**：把对话中出现的、关于站主的信息分类沉淀——已确认事实、待审核的推断、
   访客自身的兴趣信号、结构化的个人资料字段——分别存储，而不是混在一起
5. **人工审核后台**：访客对话推断出的信息不会直接生效，需要站主本人在后台确认/拒绝，
   冲突情况下人工裁决，并提供真正的"清除某条记忆"的操作入口

## 三、技术选型权衡

> 每一条都按"选了什么 / 为什么 / 放弃了什么 / 代价是什么"展开——这是面试里最容易被追问
> 细节的部分。

### 1. 两个仓库拆开，而不是一个 monorepo

- **选了**：my-web（展示层）和 my-web-agent（RAG 服务）是两个独立仓库，my-web 只通过
  一个 `/chat` HTTP 接口对接，不 import agent 的任何代码
- **为什么**：agent 服务的核心能力（"喂一个 markdown 目录，提供问答"）跟 my-web 这个
  具体站点没有必然关系，拆开之后 agent 可以被任何其他项目复用，接口即边界，强制自己
  不去抄近路直接改对方内部实现
- **代价**：调试要跨两个进程/两个终端，排查问题时链路变长（前端 → my-web 代理 →
  agent → LLM/向量库），比单体应用多一层网络跳转和序列化开销

### 2. 向量库选 LanceDB（本地嵌入式），不是 Pinecone/Weaviate 等托管服务

- **选了**：LanceDB，嵌入式、本地文件系统存储，不依赖外部服务
- **为什么**：个人项目规模（一个人的笔记库，量级在几千个 chunk 以内），托管向量库的
  网络延迟和账单成本完全不成比例；LanceDB 直接跑在同一进程里，没有额外的网络 IO
- **放弃了什么**：托管服务的分布式扩展能力、多副本高可用——但这些是千万级数据量才需要
  考虑的问题，现在要这些能力属于过度设计
- **代价**：没有现成的运维工具链（备份、监控面板），出问题需要自己处理文件系统层面的
  数据恢复

### 3. 切块策略：标题边界 + 递归字符切分，不是固定长度硬切

- **选了**：先按 Markdown 标题（`#`/`##`/`###`）切大块保留文档结构，每块记录标题路径
  作为检索时的来源标注，再用 `RecursiveCharacterTextSplitter` 按"段落 > 换行 > 中文
  句号 > 英文句号 > 空格"的优先级递归细切，只在真正超长时才切割
- **为什么**：固定字符数硬切会在句子中间断开，检索命中的片段读起来是半句话，语义完整性
  被破坏；按标题先切一刀，保证至少不会把两个不相关主题的内容拼进同一个 chunk
- **代价**：对结构混乱、不规范使用标题层级的笔记，切块效果会退化成接近固定长度切分

### 4. 记忆系统分层存储（四张表），不是一张表 + type 字段

- **选了**：`confirmed_facts`（已确认事实）/ `pending_observations`（待审核推断）/
  `visitor_signals`（访客兴趣统计）/ `profile_card`（结构化槓位字段：手机号、当前城市
  等）四张表分开，而不是一张表加 `type` 区分
- **为什么**：这四类数据的读取路径完全不同——confirmed_facts 要走向量检索排序后
  top-K 拼进 prompt；profile_card 是无条件全量加载进 system prompt，不经排序；
  visitor_signals 完全不参与回答，只是统计。混在一张表里，每次读取都要多一层 type
  过滤，而且容易在某个读取路径里漏过滤条件，造成不该曝光的数据被带进答案
- **放弃了什么**：表结构更简单、迁移成本更低的单表方案
- **代价**：四张表之间的关联（比如 pending_observations 审核通过后要迁移进
  confirmed_facts）需要额外的状态机维护，不是单表 UPDATE 一下 type 字段那么简单

### 5. 结构化槓位（profile_card）用确定性键值覆盖，不是向量相似度判断更新

- **选了**：手机号、当前城市、当前公司这类"任一时刻只有一个当前值"的属性，单独开一张
  固定枚举槓位的键值表，写入是 UPSERT by key
- **为什么**：这是本项目里最值得讲的一个决策——最初设计是把一切都塞进 `confirmed_facts`
  自由文本表，靠余弦相似度 >0.85 判断"这条新记忆是不是在覆盖旧记忆"。但手机号这类字符串
  改一位数字，向量距离可能看起来"足够相似"也可能"完全不像"，相似度本身衡量的是语义接近
  程度，不是"这是不是同一个字段"——用概率去判断一个本质上是确定性操作（覆盖/不覆盖）
  的问题，是方法和问题不匹配。拆成键值表后，更新变成直接按 key 查、按 key 覆盖，不需要
  判断相似度，也顺带解决了"旧状态和新状态谁更权威"这个时间状态管理问题（覆盖操作本身就是
  确定性的，没有"模糊地带"）
- **放弃了什么**：统一存储、统一检索逻辑的简洁性——这类数据单开了一条特殊路径
- **代价**：安全边界要单独收紧。因为这张表是无条件全量注入每次回答的 system prompt
  （不经检索排序，曝光面比 confirmed_facts 更大），访客推断出的槓位更新必须经过人工审核
  才能写入，不能因为"结构简单"就放宽这条规则

**延伸：双时间戳，而不是单一个"更新时间"字段**

- **选了**：`profile_card` 每条记录带两个时间戳——`valid_time`（这件事在现实世界里
  从什么时候起成立）和 `updated_at`（系统什么时候写入的），UPSERT 的覆盖判断用
  `valid_time` 比较，不是单纯按写入顺序覆盖
- **为什么**：只按写入顺序覆盖会在**消息乱序到达**时出错——比如"上周我在上海"因为
  处理延迟，在"这周我在北京"已经写入之后才被处理完，单时间戳方案会用这条更旧的事实
  覆盖掉已经写入的新事实，而双时间戳能通过比较 `valid_time` 识别出"这条虽然后到，但
  描述的是更早的状态"，从而拒绝覆盖
- **放弃了什么**：单时间戳的简单性——多一个字段，多一次比较逻辑
- **代价**：对大多数场景（用户说的当下就是生效的当下）这个字段是冗余的，只在少数乱序
  场景下才体现价值，是用"現在多付一点代价"换"以后不用做数据迁移"的选择

### 6. 冲突检测用阈值 + 人工裁决的混合策略，不是纯自动化

- **选了**：余弦相似度 >0.85 自动判定为同一事实的更新（supersede），中间地带的相似度
  标记为"待裁决"，交给人工审核界面处理，不自动判断
- **为什么**：全自动化在边界case上必然出错——阈值定高了会漏掉真实的矛盾（两条事实都
  留在库里，回答时互相打架），定低了会误伤不相关的两条记忆（错误覆盖）。承认"模型判断
  不了的中间态需要人介入"，比硬凹一个"更聪明的阈值"更诚实，也更稳
- **代价**：多了一个需要站主人工处理的审核队列，不是全自动运行的系统

### 7. 遗忘淘汰机制刻意推迟到有真实数据量之后再设计

- **选了**：当前阶段不实现基于重要性打分/访问频率的记忆淘汰机制，只在表结构里预留
  `access_count`、`last_accessed_at` 等字段占位
- **为什么**：时间衰减权重、重要性评分这类多因子打分公式，在记忆条目只有几十条、没有
  真实使用数据验证的情况下定下来，大概率是在对着自己脑补的测试场景过拟合，上线后遇到
  真实分布反而要推翻重调。先把表结构的扩展口子留出来（避免以后要迁移数据库），把权重
  公式这种"必须靠真实反馈才能调对"的部分往后放，是经过取舍的决定，不是漏做
- **代价**：短期内没有自动清理机制，记忆库会持续增长，需要定期人工检视

### 8. 身份识别放在 my-web 侧（JWT 登录），不是 agent 侧

- **选了**：管理员登录、角色判断发生在 my-web；agent 侧只信任一个共享密钥校验过的
  `role` 字段，自己不做登录逻辑
- **为什么**："谁是站主本人"是网站层面的概念（登录态），"这段对话内容要怎么分类存储"
  是 agent 层面的概念，职责边界清楚；并且 agent 要同时可能被其他项目复用，不应该绑定
  my-web 特定的登录实现
- **代价**：引入了跨服务的信任传递问题——必须先有共享密钥校验这层，否则任何调用方都能
  在请求体里自称 `role: owner`，这是设计里排第一优先级要堵的安全缺口

## 四、已知的简化和权衡（面试中可能被追问"为什么没做 X"）

- 检索 query 目前只用"最新一句话"算向量，不做多轮对话的指代消解（query rewrite），
  因为这需要多一次 LLM 调用，且判断逻辑和"记忆固化"层性质相近，当前阶段选择接受
  "追问类问题检索可能不准"这个代价，而不是提前做
- 只做语义记忆（陈述性事实），不做情节记忆（具体某次对话发生了什么），因为当前场景
  没有"回忆某次具体交互"的真实需求，情节记忆是完全不同的存储和衰减策略，不是语义记忆
  加个字段就能兼容的
- 不做知识图谱式的实体关系建模，profile_card 的槓位是预先枚举的固定集合，不是动态
  schema——现在的数据量和需求都不需要图结构的表达能力，强行上图数据库是过度设计
- 记忆的读写/遗忘规则统称为"policy"分类管理（写入 policy、召回 policy、遗忘 policy），
  但没有为此新建一个 `Policy` 抽象类或配置文件——这纯粹是文档层面的归类命名，规则数量
  少、改动频率低的阶段，提前抽象只会增加不必要的间接寻址，不是一个有真实工程代价的选型
